---
title: Set up judging
description: Create prizes, invite judges, share the work, and publish winners.
---

Open **Judging** from your event's manage page. It has four places: **Overview**, **Judges**, **Settings**, and **Results**. Old judging links still open the matching page.

## Start with the basics

1. **What can teams win?** Add a prize name, reward, and optional description.
2. **What should judges look for?** Save the starter scorecard or write your own questions.
3. **Who's judging?** Paste email addresses and preview who will be added or invited.
4. **When should they judge?** Set the opening, deadline, and time zone.
5. **Who reviews each project?** Preview the work, check missing judges, then apply it.

You can complete each step from Settings or from a sheet in **Action Items**. Saving one step doesn't require finishing the others. Judging can't open while required setup is missing.

The starter scorecard has four questions, each worth 25% and scored from 0 to 10: **Original idea**, **Does it work?**, **Easy to use**, and **Usefulness**. It is created only when you choose **Use this scorecard**. Existing events keep their setup.

We suggest three judges per project and a two-hour judging window after projects close. If fewer judges qualify, the assignment preview explains the gap. Judges can't review their own teams. Prize and room limits are respected.

## Choose how each prize works

Open **More judging options** to use any of these methods:

| Method | What judges do |
| --- | --- |
| Score projects | Answer shared and prize-specific questions. Weighted scores determine rankings. |
| Check requirements | Answer yes or no for each requirement. |
| Sort into groups | Choose a group using the descriptions you provide. |
| Pick favorites | Choose and order favorites from their assigned projects. |
| Audience votes | Let eligible attendees vote under the event's voting rules. |

Shared questions are answered once per project and reused only for prizes the judge is assigned to. The scorecard preview shows the questions and weights that apply to each prize.

Optional rounds let you pick a shortlist before a final review. Each round can inherit the event's judging dates or use its own. Moving projects into the next round requires an explicit selection or an approved rule and a completed review of the previous round.

## Keep saved reviews safe

Judges have one assigned queue with **To review**, **In progress**, and **Submitted** filters. Each review has its own URL. Partial answers and private notes save as drafts; drafts don't affect results. **Submit review** publishes a complete decision. Changes to a submitted review stay separate until **Save changes**.

Once reviews are submitted, scoring rules and project eligibility are locked. Prize names and reward details remain editable. Start a new round to change scoring; old answers aren't silently copied or recalculated.

Assignment previews add missing work. They never silently remove existing reviews. Individual adjustments remain available, while completed reviews stay protected.

## Dates and reminders

Event end, project close, and judging close are separate. Judging can happen after the event ends. Events with no judging dates retain manual opening and closing. Closing judging keeps drafts and submitted reviews available to read; it doesn't publish results.

Invitations send when the event is live. Draft-event invitations wait for publication. Judges can control email preferences and quiet hours in their judging inbox. Routine reminders use the selected time zone; opening and imminent-deadline notices follow their scheduled time.

For a two-hour session, unfinished work gets an opening notice and a one-hour-remaining reminder. Completed work and stale reminders are suppressed. An email marked **accepted by the provider** is not proof that it reached someone's inbox.

## Use an agent or the CLI

WebMCP can inspect and configure judging, save prizes and scorecards, invite judges, and preview or apply assignments. These tools use the same permissions, timing rules, revisions, and retry keys as the app. See [WebMCP](/docs/guides/webmcp) and the [CLI judging guide](/docs/guides/cli-judging).

The canonical setup endpoint is `GET /api/dashboard/hackathons/{id}/judging/setup`. To save settings, `PATCH` the same path with its `expectedVersion` and a stable `requestKey`. Reuse that key when retrying the same change. A conflict asks you to reload the current setup while preserving your draft.
